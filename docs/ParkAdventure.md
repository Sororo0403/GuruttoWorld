# こもれび公園の基準ステージと制作時の自動生成

タイトルの START から `Assets/Scenes/ParkAdventure.json` を遊べます。
Editor ではこのシーンを開き、Game にフォーカスを置いて Play します。
移動は WASD・矢印・左スティック、ジャンプは Space・A、攻撃は J・X、再挑戦は R・Start、タイトルへ戻る操作は Esc・B です。

ジャンプ後にボタンを押し続けると、上昇開始から0.25秒後に最大0.85秒の空中停止が使えます。
空中停止はホバリングの操作を試すための暫定仕様です。上昇する飛行やコピー能力は実装していません。
敵への攻撃は近距離の範囲攻撃です。敵や収集物との間に壁がある場合、Raycastで判定して攻撃・収集を防ぎます。
敵に触れるとライフが減り、一定時間は連続ダメージを受けません。落下やライフ切れで最後のチェックポイントへ戻ります。
収集物とスイッチの進行は復帰時に保持され、再挑戦でリセットされます。

ステージは導入、段差への寄り道、水路のジャンプ、左右のスイッチ、展望台の順です。
花のかけら12個は任意の収集目標で、出口は2つのスイッチを踏むと開きます。
奥のランドマークを示す自動カメラ、攻撃の白いエフェクト、進行に応じた操作説明とクリア表示を含みます。
今回のモデルはリポジトリ内のプリミティブと専用パレットによる試作用アートです。
ディスカバリーと同等の完成アート・アニメーション・音響・ステージ密度を達成したものではありません。

## モジュールと生成

`Content/Assets/Prefabs/Park` に5つの編集可能なPrefabを保存しています。
生成器はこれらを読み、モジュールのルートをワールド座標へ焼き込んだ通常のシーンを出力します。
キャラクターの目・足などの親子関係は維持します。生成した配置とPrefabはライブ接続されません。
Prefabを編集してから生成すると、その内容を使って次の候補を作れます。

```powershell
python scripts/GenerateParkAdventure.py --seed 7 --output generated/park/Candidate7.json
```

同じSeedと同じPrefabから同じ候補が作られます。Seedは段差エリアの左右反転と木・花の配置を変えます。
主ルートと仕掛けの順序は固定し、まず基準ステージの品質を保持する範囲に限定しています。
既存ファイルは `--overwrite` を指定した場合だけ置換します。
候補をEditorで再生する場合は、次のようにAssets/Scenesへ直接出力してください。
出力するシーン内の再挑戦先も、そのシーン自身に設定されます。

```powershell
python scripts/GenerateParkAdventure.py --seed 7 --output Content/Assets/Scenes/ParkCandidate7.json
```

標準の基準ステージを再生成する場合:

```powershell
python scripts/GenerateParkAdventure.py --seed 20261012 --output Content/Assets/Scenes/ParkAdventure.json --overwrite
```

`--author-library` はモデル・マテリアル・Prefabの初期ライブラリも再作成します。
手で編集したPrefabを置き換えるため、通常の候補生成には指定しません。
ビルド時に生成器は実行せず、保存済みシーンを使用します。
生成の記録と構造検査結果は `generated/park/reports` に保存します。

## ゲーム処理のビルド

`Content/Assets/Scripts/ParkAdventure.cpp` を既存のC++ゲーム処理の自動コンパイル機能で読み込みます。
Editorを起動するとソースの変更が検出され、対応構成のモジュールがコンパイルされます。
Appを直接実行する場合は、Appをビルドした後で、対応するゲーム処理を実行先に出力します。

```powershell
MSBuild App/App.vcxproj /p:Configuration=Development /p:Platform=x64
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/BuildScripts.ps1 -Configuration Development -OutputContent generated/outputs/x64/Development/App
```

配布は既存の `scripts/BuildPlayer.ps1` を使用します。保存済みC++ソースを配布用にコンパイルし、DLLとCRTを同梱します。

## 検証

```powershell
python -m unittest discover -s tests -p test_park_generation.py -v
MSBuild tests/ParkAdventureValidation.vcxproj /p:Configuration=Release /p:Platform=x64
generated/tests/outputs/x64/Release/ParkAdventureValidation/ParkAdventureValidation.exe
```

Python検証は100種類のSeed、再現性、重複ID、親参照、スイッチと扉の順序、中央ルートの足場欠落を確認します。
ジャンプ距離は通常ジャンプの理論距離に安全係数を掛けた構造検査です。動く足場や自由な地形には対応していません。
C++検証は実際のJoltキャラクターとゲーム処理でコースを進み、空中停止の制限、戦闘、12個の収集、落下復帰、扉、クリア、再挑戦を確認します。
通し検証はReleaseを推奨します。Debugも同じ検証を実行できますが、CPUでの再生に時間が掛かります。
描画はSceneEnvironmentを使って検証し、入口と水路の画像を `generated/park/previews` に保存します。

次の拡張では、操作感のプレイテスト、完成用モデルとアニメーション、効果音、場面ごとのカメラ設定、場面の固定・部分再生成を進めます。
現状は制作時の候補生成です。プレイするたびの生成、生成AIによる企画、任意のPrefabを対象とする自動攻略検査は含みません。

## 軽量化とCC0モデル（2026-10-12）

木と花はKenney公式のNature Kit（CC0 1.0）のOBJ/MTLを使用する。元の色を保ち、テクスチャを必要としない低ポリゴンモデルを選択した。配布元は https://kenney.nl/assets/nature-kit 。`Content/Assets/Models/Park/KenneyNature/License.txt`に元ライセンス、`Source.json`に取得URLとZIPのSHA-256を保存している。プレイヤー・敵・ベンチ・地形は従来の自作形状。

装飾の木と花は複数の球体から各1モデルへ統合し、ステージのオブジェクト数は246から162に減った。木は1本196三角形、花は黄色78三角形。コライダー、ルート、収集物、攻略条件を維持する。

スクリプトのコミット時には`SceneLayout::Validate()`を使用する。保存時と共通の読み込み検証をJSONオブジェクトへ直接適用し、毎フェーズの文字列化とJSON文字列の再解析を省く。トランザクションとエラー時のロールバックは維持する。破棄時のStopコールバック用の旧配置コピーも、Stopを持つオブジェクトだけに絞る。保存フォーマットは従来どおり。

同じPCのRelease版、入口で40回の固定更新＋Component更新を計測したCPUシーン更新は17.87ms/回から6.49ms/回へ短縮（約64%）。モデル読み込み・描画時間を除く計測であり、FPSやGPU時間ではない。`ParkAdventureValidation`はこの値を出力する。未最適化のDebug版は性能比較に使用しない。実際に遊ぶ際はRelease配布版を使う。

## 配布版のカクつきの原因調査（2026-10-12）

ユーザーの対象は配布版App.exe。Release構成の共通SceneEnvironmentで、1280×720の実描画を含めた120フレーム×3シナリオを測定した。初期化直後の10フレームを除いて集計し、CSVには初期フレームも残す。数値は同じPCでの一例で、異なる解像度・GPUでの性能を保証しない。

| 条件 | CPU更新の平均 | 最大 | GPUの最大 |
| --- | ---: | ---: | ---: |
| 入口で静止 | 6.22ms | 7.55ms | 0.24ms |
| 収集物へ歩く | 7.99ms | 203.56ms | 0.24ms |
| ジャンプと空中停止 | 6.43ms | 8.66ms | 1.25ms |

収集物を1個取った28フレーム目で約0.20秒停止した。同じ条件の再実行でも約214msを再現。最大フレームではCPU更新203.56msのうち、描画資源の再構築178.66ms、UI再生成18.20ms。GPU時間0.23msは完了済みフレームの遅延サンプルであり、CPU停止フレームと完全に同期した値ではない。周辺のGPUサンプルも軽く、測定条件ではGPU飽和よりCPUの再構築が支配的。

主因は`SceneWorld::PrepareScriptLayout`がオブジェクト数の変更だけで全描画配置を`PrepareLayout`し直すこと。そこからシーンのアセット解決と各マテリアルのLoadが走り、`MaterialAsset::Load`の`AssetDatabase(root)`が毎回Assets/Shadersを再帰探索して全metaを読み直す。最大フレームではマテリアル分だけで12回・108.64ms、シーンのアセット解決は別に25.44ms。平均のCPU更新時間だけを見ると、この単発の停止を見落とす。収集物以外の敵・スイッチ・ゲートの削除にも同じ再構築経路が使われる（これらのイベント別ピークは未計測）。

副因はカウンターや案内文が変わる際の`SceneUi::PreparePart`。文字の画像を再生成・同期アップロードし、2種類のSpriteRendererでUIシェーダーのコンパイルとPSO生成を行う。今回の収集時は18.20ms。60Hzの1フレーム予算16.67msをこれだけでも超える。

継続的な移動の小さな段付きも別に確認した。1/144秒の更新を120回行う再現では、70回でプレイヤーの位置が変わらず、残りで約0.0833mずつ進む。物理は1/60秒の固定ステップで、描画側が直前・最新の物理姿勢を補間していないため。これは144Hz相当の更新を与えた位置サンプルによる検証であり、実際の144Hzモニター上の表示は未確認。

優先する修正は、(1) 削除時に生存オブジェクトのモデル・マテリアル資源を再利用し全アセット探索をしない、(2) UIのシェーダーとPSOを再利用して文字画像の更新だけにする、(3) 描画時の物理姿勢補間を導入する、の順。本調査では挙動を変えず、計測区間と再現手順を追加した。

ジャンプ・空中停止は実際に高さ1.3m超と重力OFFを確認して測定した。重力の切替で物理ワールドも再構築されるが、それぞれ約2msで今回の大きな停止の主因ではない。

参考としてDebug構成は入口のCPU更新が132.93ms/回だったが、ユーザーが使用しているRelease配布版とは分けて扱う。

`WP1_PARK_STUTTER_ONLY=1`で専用検証を実行すると`generated/park/stutter.csv`と`generated/park/motion-144.csv`を出力する。フレームごとのCPU更新、Render/Present、GPUサンプル、再構築と探索の内訳、探索回数、プレイヤー位置を記録する。Render/PresentにはVSync待ちも含む。CPU区間は包含時間なので合計すると二重計上になる。

## カクつきの修正（2026-10-12）

実行中の配置変更はIDで差分を取り、生存するモデル・マテリアル・Animatorの個体を保持する。削除だけでは全配置の資源を作り直さない。実行用のアセット索引とメタデータはシーン準備時に一度保持し、明示的な再読み込みでは最新の索引を構築する。モデル・マテリアル・UIの候補が失敗した場合は既存の配置と表示を保持する。

UIとモデルの不変なルートシグネチャ・PSOを共有し、Spriteの四角形も再利用する。モデル個体ごとの骨・照明・インスタンスの更新バッファーは共有しない。シェーダーのキャッシュはソースとincludeの実内容、entry、target、コンパイル設定で区別し、同じサイズ・時刻の編集も検出する。通常のUI更新は確定済みのパイプライン世代を使い、明示再読み込み時に変更を検査する。

旧描画資源は同じデバイス・キューの完了フェンスまで保持してから解放する。文字変更では既存の描画パイプラインを使って文字画像を差し替え、同じ描画キューへ転送を送る。転送用バッファー・コマンド・画像を完了フェンスまで保持し、通常の文字変更ではCPUでGPU完了を待たない。重力・移動速度・ジャンプ速度の変更では、Joltキャラクターを再生成せず現在の設定を適用する。

物理は従来の60Hzで更新し、描画だけを前回・最新の確定姿勢の間で補間する。子の配置とカメラにも補間を反映する。保存・当たり判定・ゲーム処理は確定した配置を使用する。2mを超える移動、拡縮、親変更、直接の姿勢編集は即時反映する。遅れたフレームの追いつきは最大4固定ステップに制限し、残った整数ステップを捨てて描画への復帰を優先する。

`WP1_PARK_RESOURCE_ONLY=1`の専用検証は、シェーダーの共有・変更検出、日本語パス、実行中の生成・削除・文字変更、失敗時の保持、補間と子の追従、直接移動、追いつき上限を確認する。時間のしきい値ではなく、温まった資源更新で全アセット探索・コンパイル・PSO生成が発生しないことを検証する。
最終Releaseを同じPC・1280×720で再計測した結果は次のとおり。ビルドや別のGPU検証を並行実行しない状態で測定し、初期10フレームを除外した。

| 条件 | CPU更新の平均 | 最大 | GPUの最大 |
| --- | ---: | ---: | ---: |
| 入口で静止 | 7.31ms | 11.17ms | 0.24ms |
| 収集物へ歩く | 7.08ms | 10.52ms | 0.24ms |
| ジャンプと空中停止 | 7.29ms | 11.34ms | 0.25ms |

取得した28フレーム目のCPU更新は203.56msから9.78ms（約95%短縮）、UI更新は18.20msから2.81msとなった。そのフレームの全描画配置の再構築、シーンアセット解決、マテリアル用の全meta探索は0回。削除後の物理ワールドは次の固定更新で再構築するが、物理の削除・ID再対応付けの安全性を維持し、この測定の最大更新は10.52msに収まった。取得以外のイベントも実行中の差分更新検証と全コース攻略で確認したが、敵やゲートごとのピーク時間は個別計測していない。

144Hz相当の120更新では、確定した物理位置の繰り返しは70回のまま、描画位置の繰り返しは開始直後の2回だけになった。途中の移動は毎更新補間される。実際の144Hzモニター上の表示は未確認。これらはCPU区間・位置サンプルの比較であり、FPSを保証する測定ではない。

全コースは1924フレームで12/12収集とクリアを再確認した。従来の40回静止更新によるCPU計測は6.48ms/回で、前回の6.49msとほぼ同じ。Appとゲーム処理DLLのDebug・Development・Releaseビルド、Releaseの資源・物理・UI・Animator・Material・ライト・HDR・Editor回帰、DebugのUI転送と資源寿命検証が成功した。Release配布物は公園を一時的な起動対象にして読み込み・更新・描画を確認し、タイトル起動へ戻してハッシュを確認した。

文字の画像化は従来のGDI方式を維持しており、文字ごとのアトラス化は含まない。今回の取得時は描画パイプライン共有と非同期転送で2.81msとなった。確定したアセット索引の更新とシェーダー変更の検査は明示的な再読み込み時に行う。
